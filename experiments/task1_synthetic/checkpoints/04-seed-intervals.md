# Чекпоинт 04: шум сидов и интервалы для Δρ̄ и recall

Дата: 2026-11-08. Таблицы: `results/task1/rho_ci_laion1m.md`, `rho_ci_laion10m.md`, `rho_ci_laion10m_gens.md`. Запуск: [04-run.sh](04-run.sh), склейка `logs/iter14.sh` и `logs/iter15.sh`; выравнивание остальных кривых до 10 сидов — `logs/iter16.sh`

## Зачем

До этого вердикты по ρ держались на трёх сидах balanced k-means и одном-двух сидах генератора. У самого LAION ρ между сидами гуляет на ±0,008, при пороге 0,02 этого мало, чтобы отличить «проходит» от «проходит на уровне шума». Нужен интервал для Δρ̄, в котором учтены все три источника шума: разбиение, выборка запросов и генератор

## Как считается

`rho_ci.py` пересчитывает ρ(q) по каждому запросу из сохранённых разбиений и gt, базу он не читает. Для датасета с n сидами: SE_seed = sd(средних по сидам) / √n, SE_q = sd(средних по запросам) / √nq, SE = √(SE_seed² + SE_q²). С сидами генератора каждая реплика генератора даёт одно среднее, SE = sd(средних реплик) / √G. Вердикт по max_k (|Δ| + 1,645·SE_Δ):
- «с запасом»: граница ≤ 0,02
- «по точечной»: max_k |Δ| ≤ 0,02, но граница выше
- «нет»: точечная оценка больше 0,02

## Что запущено

- 10 сидов k-means для laion1m, s1m-fp-blur1.0, laion10m, s10m-fp-blur1.0, оба набора запросов
- сиды генератора: g1–g4 на 1M (по 3 сида k-means), g1–g2 на 10M (3 сида, только heldout). Базы после прогона удалены, `generate` с тем же `--seed` их воспроизводит (md5 g1 совпал, `logs/*.md5`)
- SE recall@100 по запросам: RaBitQ 4–8 бит на 1M (1000 запросов), 7 бит на 10M (5000 запросов). Средние recall совпали с прогоном до SE (`quant: средние совпали` в `logs/iter14.log`)
- iter16: cuVS (s1m-fp, s10m-fp) и 10k кл. + blur (s1m-nc10k, s10m-nc10k) догнаны до 10 сидов. Перегенерированные базы сверены по md5 gt и запросов, сбоев нет

## Главная находка: оракул на 10M занижен систематически

На 10M Δ оракула при k = 1 −0,0196, 95% интервал [−0,029; −0,011]. С сидами генератора −0,018, интервал 0 не содержит. Дальше по k: −0,010 при k = 2, −0,005 при k = 3, −0,002 при k = 4, 0 при k = 8. По трём сидам было −0,014, и это выглядело как шум. Роутер по центроидам при этом совпадает (Δ ≤ 0,001), но только потому, что потеря роутера ρ̄_oracle − ρ̄_centroid у синтетики тоже на 0,02 меньше. Ошибки компенсируют друг друга

Механизм (`viz_blur.py`, раздел «Что blur делает с распределением» в README):
- оракул при k = 1 идёт за долей кластера генератора запроса в главном шарде: корреляция по запросам 0,80 на 10M и 0,76 на 1M
- blur превращает гауссово облако в звезду до 8 соседних центроидов, и balanced k-means режет её чаще: в главном шарде 0,69–0,70 кластера против 0,74 без blur, на обоих масштабах
- поэтому blur снимает с оракула 0,026–0,027 и на 1M (0,785 → 0,759), и на 10M (0,807 → 0,780)
- масштаб меняет точку отсчёта. cuVS без blur завышает оракул на 0,021 на 1M и на 0,007 на 10M: у LAION оракул от 1M к 10M растёт на 0,035, у cuVS на 0,022. На 1M сдвиг blur гасит завышение, и совпадение случайное, на 10M остаётся −0,020

## Побочная находка: смещённая выборка для хабов

`stats.py` считает скошенность N₁₀ по первой половине отсортированной случайной выборки строк. База синтетики записана кластер за кластером, поэтому для синтетики эта выборка покрывает половину кластеров. По равномерной выборке на 1M: LAION 3,85 (было 3,76), cuVS 3,96 (было 2,27), cuVS + blur 26,5 (было 24,4). Вывод «хабы в 7 раз сильнее» остаётся, но хабы даёт только blur: cuVS без него по хабам совпадает с LAION. Почему blur даёт хабы, разобрано в README. Сам `stats.py` не исправлен: тогда пришлось бы пересчитать статистики всех датасетов, а базы части из них удалены
